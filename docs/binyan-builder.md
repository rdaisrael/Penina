# Penina Binyan Builder

Route: `/PeninaPlus-Binyan-Builder/`.

## Current scope

Learn offers all seven binyanim: קל (פעל), פיעל, הפעיל, התפעל, נפעל, פועל and הופעל, independently of the workbook's learned marks. Each has an All root types selection; the Reader's specific root groups are also available, alongside Shalem Pual/Hufal. Supported forms are past, present, future, infinitive, imperative and verbal noun, except Pual/Hufal, which offer only past, present and future. A form is available only when its complete paradigm is recorded in the local dictionary catalogue.

The shared Reader parser is unchanged. The download uses Reader's current `Vocabulary_By_Category.xlsx`, and uploads accept `.xlsx` and `.xls`, including older Reader workbooks. Practice follows the exact X-marked binyan/root-type/tense squares, including verbal nouns, on both client and server; it never takes a cross-product of learned binyanim and tenses. Switching from Learn to Practice discards unmarked selections. Unsupported combinations are filtered out of the selector, not treated as a corrupt workbook; all learned forms remain available for assessing context vocabulary. The current Reader template has no Pual/Hufal or All root types rows, so those selections are available in Learn only. Learn needs only roots. Select one visible combination directly or enable mixed practice for up to eight combinations; worksheets have 6–30 questions, model tables in Learn, and a separate printable answer key.

The Pattern selection control defaults to **Standard pattern**; **Exceptions** is separate in both Learn and Practice. Eligibility is determined by the exact dictionary lexeme, binyan, root type and tense/form. All root types admits the verified root classes in the chosen classification, including four-letter roots. Specific root groups restrict eligibility further. Unknown or incomplete combinations are unavailable, never assumed to be exceptions. “Which uploaded roots fit?” lists standard, exceptional and unverified roots for every selected combination. No eligible roots stops generation locally and on the server before either external service is called; a small pool may repeat. Choice exercises additionally require an attested alternative with different consonants.

## Dictionary catalogue and pattern classification

`verb-data.js` contains 2,034 verb entries adapted from English Wiktionary through Kaikki.org (2026-10-01 dump, 2026-10-30 extraction). Each entry retains its source link, binyan-specific meaning, individual pointed forms and classification for each complete tense. The data and annotations are CC BY-SA 4.0; see `PeninaPlus-Binyan-Builder/VERB-DATA-LICENSE.txt`. Attribution appears in the builder, student worksheets and answer keys; individual source links appear in the key. The raw 60 MB source is not committed.

`scripts/build-binyan-catalogue.js` imports explicit conjugation-table records. It excludes senses marked archaic, rare, Biblical, literary or otherwise unsuitable, and omits incomplete paradigms. It uses the first listed pointed form per cell and the builder's existing modern shared feminine-plural future/imperative convention. A few irregular tables need explicit root/binyan identities; their forms still come only from the source. Homonymous entries remain separate. לבש/Piel is explicitly excluded in both selections. A verbal noun must be listed as `noun-from-verb` in that verb's conjugation table: an independently analyzed noun is insufficient evidence of the root/binyan relationship.

`lib/binyan-patterns.js` compares every retained person form against a named model for the selected root type. Regular models are כתב (Kal, Hifil, Hitpael, Nifal), סדר (Piel), ספר (Pual) and כנס (Hufal). Existing weak groups use בנה, קום, נפל, ישב, נסה, פנה and ירד as applicable. The comparison accounts for equivalent pointed full/defective spelling, ordinary light dagesh and final-kaf silent sheva while retaining vowel changes, consonant changes and required strong dagesh. Every cell must match for that tense to be standard. The comparator never supplies new verb forms; the dictionary supplies them. A weak group without its own established model retains its root type and is compared with the binyan's regular model.

For example, למד/Kal is standard in the past but exceptional in the future and imperative. נגן/Piel is standard in the present but its sourced past paradigm differs. Weak verbs may be standard within their own model: היה follows the ל-ה future pattern but differs in the past. A lesson identifies its reference model when explaining an exception. This is a finite, mechanically classified dictionary catalogue, not a claim that every Hebrew verb or every usage label has been independently reviewed. Missing forms stay unavailable until source data is added and rebuilt; dictionary errors and context suitability still require teacher review.

To rebuild from the documented Kaikki JSONL snapshot, run `node scripts/build-binyan-catalogue.js /path/to/kaikki.org-dictionary-Hebrew.jsonl`. The builder records the input SHA-256 and reports standard/exception counts by binyan and form. The snapshot checksum is `c1c6abf161b8a7ff96922a95bb4ba098373b1e4217cad29b0ca9f002d9394204`. Review changes to source records, model comparisons and attribution before replacing the catalogue. The Reader's older conservative 16-root Kal-infinitive mastery list remains unchanged; only Binyan Builder uses the expanded catalogue for exercise eligibility.

## Generation and verification

`/api/generate` with `action: "binyan-worksheet"` dispatches to the existing server-only OpenAI adapter. Like Penina Hebrew Reader, it requests a complete structured result in one AI call, using a 110-second per-call timeout, a 32,000-token output allowance and one possible additional call. The complete 6–30-question plan is included; there are no queued question batches sharing a shorter deadline. Structural validation checks all requested pairs, persons, roots and model-table coverage together. No partial worksheet is returned. Server logs identify each AI call's phase, attempt number, question/lesson counts, duration, completion state and controlled failure code; they omit vocabulary, roots, generated content, provider bodies and credentials.

Before Dicta, every model form and question answer must match the exact selected catalogue entry, person and classification. Choice alternatives must come from that same lexeme, although their alternative tense can have a different classification. Equivalent pointed full/defective spellings are accepted, but wrong vowels, dagesh or shin/sin pointing are rejected. The prompt includes the source forms and meanings for up to eight eligible roots per pair, with at most 24 root/pair references overall to bound prompt size. English target meanings are taken from the reference before returning the worksheet.

`lib/binyan-dicta.js` then verifies every distinct model/answer form. Fully pointed candidates are submitted with `keepnikud: true`, `matchpartial: false`, `addmorph: true`, and `freturnfullmorphstr: true`. Pronoun context disambiguates personal/present forms; אָנָּא disambiguates imperatives. For verbs, the BGU analysis must match root, the selected binyan, tense, person, gender, number and vowelled answer, with no extra prefix/suffix. Verbal nouns require an exact catalogue-associated form and matching noun analysis; the noun analyzer is not used to infer the binyan. Dicta's final י root notation is accepted for the corresponding final ה root across binyanim. Standard modern shared feminine-plural future/imperative forms are accepted. Missing, misaligned, unknown or mismatched analysis fails closed: no unverified worksheet is returned.

Production uses the existing `DICTA_API_KEY` and keyed Nakdan endpoint. Local live checks without a key use Dicta's public endpoint. No secret is sent to the browser. Only form/context text is sent to Dicta, not the workbook or filename. The worksheet generator receives the vocabulary lists and selected patterns, while the original workbook remains in the browser. A transient initial AI failure may retry once. This retry and the morphology correction below share one additional-call budget: there are never more than two AI calls. Permanent provider errors are not retried. Each AI call allows up to 110 seconds, and each Dicta call up to 25 seconds, all capped by one 275-second server deadline. The browser allows 285 seconds, below the existing routed function's 300-second limit. Service errors retain the previous successful worksheet. Provider timeouts, connection failures and cancellation have distinct controlled error codes; timeouts explicitly tell the user that AI generation took too long.

When the catalogue comparison or aligned Dicta analysis rejects forms, the verifier collects all mismatches in the batch. If the extra AI call has not already been used for a service retry, one correction pass replaces the affected root/pair's lessons and questions, including rejected choice distractors. It prefers another eligible uploaded root already used without a mismatch elsewhere in the worksheet; if alternatives exist, the rejected root is excluded for that pass. A sole eligible root may instead have its forms corrected from the supplied reference. The correction must preserve target lesson pairs, classification, question numbers, persons, exercises and counts; it cannot add questions or introduce roots outside the workbook. Meanings, model tables, sentences and vocabulary analysis are replaced together where needed. The merged worksheet goes through structural, catalogue, vocabulary and full Dicta verification again. Missing/malformed Dicta analysis and Dicta service outages are not treated as linguistic failures to regenerate. A second rejection stops; there is no retry loop and no unverified fallback.

Dicta verification is not a proof of general linguistic accuracy. Its contextual analysis can reject valid ambiguous forms. Explanations, context sentences and supporting vocabulary glosses remain AI-generated and are not validated semantically by Dicta. Target meanings come from the dictionary. Review worksheets before classroom use.

## Exercise variety (September 17)

Teachers can select any of four exercise types, all selected initially: circle the correct form, conjugate for a pronoun, complete a sentence, and write an original sentence. The requested total question count is divided across the selected types in contiguous sections. Single-type worksheets remain available. Older API requests without `exercises` retain the conjugation-only format.

Choice distractors are catalogue forms of the same lexeme with a different number (or past versus infinitive/verbal noun), and both choices must pass Dicta. Identical consonantal choices are rejected so the distinction is not dependent on tiny vowel differences. Correct-answer placement alternates. Sentence stems require exactly one blank and cannot repeat the answer. Original-writing questions leave two lines; only the teacher key shows the example sentence, explicitly labeled as one possible answer. Dicta checks the target and alternative forms, not the entire sentence's meaning or the student's original writing.

Validation: 150 automated tests passed; browser checks cover all four rendered sections, selection validation, RTL layout and print answer isolation. A live Dicta batch verified the target and alternative forms for a ten-question mixed exercise fixture using אכל and שתה. Browser and generation tests use fixed candidate sentences; live Dicta checks separately exercise morphology validation.

The word-bank exercise and display have been removed. The remaining worksheets use the compact layout with a maximum exercise font size of 14pt on screen and in print. Repeated per-question binyan/root-type labels and translations are omitted; root cues remain where the task needs them. Printed worksheets and answer keys use a 0.75-inch left page margin.

## Familiar sentence vocabulary and notes

Generation now retains the workbook's nouns, adjectives, prepositions, adverbs, conjunctions, question words, and expressions alongside roots and learned forms. The prompt prioritizes these words when writing sentence-completion stems and teacher example sentences. This is a generation preference, not a guarantee of an entirely mastered sentence; sparse lists may still need unfamiliar context words.

Teachers can choose vocabulary notes at the bottom of each page (the default), at the end, or no notes. Placement can change without another generation request. Notes contain the Hebrew supporting word or phrase and an English gloss; the missing verb is excluded from analysis. Writing examples and their notes appear only in the teacher key. Repeated notes are deduplicated within each document and repeated on a page when needed there.

The browser and server reuse Reader's `validateAnalysis` and `buildResult` to check word alignment, uploaded matches, pronouns, expressions, and learned context-verb forms. A familiar root alone does not establish mastery of an unlearned conjugation. Missing/misaligned analysis fails before returning a worksheet. Glosses and linguistic matches are AI-generated and still need teacher review; Dicta continues to verify target verb forms, not translations or complete sentence semantics.

Pagination measures questions and notes together at the existing Letter size, repeats exercise headings on continuation pages, and reflows after a font or note-placement change. Long exceptional teaching blocks flow instead of clipping. Local validation covers all vocabulary sheets, familiar/unfamiliar words, expressions, invalid analysis, answer isolation, 30-question pagination, note placement, font changes, and mobile width. The full unit suite passed 738 tests; local browser checks use mocked generation, and the two-page PDF was inspected without contacting production or live AI services.

## Shared Reader infinitive rule

The Reader imports the same vetted infinitive lookup in the browser and on the server. In root-based vocabulary modes, Regular Kal infinitive mastery requires a listed root and matching infinitive spelling (and matching vowels when pointed). Both workbook labels and checkbox labels with parenthetical model roots are recognized. Nonstandard forms become unmastered and receive ordinary footnotes, including when the provider incorrectly reports them as mastered. The check runs again after vocalization. Other separately learned categories, complete-word vocabulary and explicitly learned expressions retain their existing behavior.
